# Context Rot 検証レポート

2026-10-12 / 実行環境: Claude Max 5x（サブスクリプション）、Claude Code 2.1.284 の headless モード（`claude -p`）

## 要旨

- **Claude Opus 5.5 は、単純な情報の検索なら 1M 付近（約 890K トークン）でも劣化しなかった。**
  日英・100K〜900K の 8 条件すべてで、20 個の値・訂正された値・出現回数を満点で答えた。
- **ただし「統合・集計」が要る課題では、887K で誤りが出た。** 離れた 2 か所の記録の組み合わせ（4/5）と、
  紛らわしい記録が混ざる中での数え上げ（7 回を 8 回と回答）。同じ課題を 97K で解かせると満点だったので、長さが効いている。
  同じ 887K でも、質問を分解すれば全問正解した。
- **compaction（会話の自動要約）を挟む長い会話では、Opus 5.5 は 300K・compaction 3 回を経ても日英とも全情報を保持した。**
- **Haiku 5.5 は、英語で compaction の要約そのものに会話中の回答ルール（「3 行以内」など）を適用してしまい、
  1 回目の compaction で覚えるべき情報をすべて失った。** Opus は compaction 用のテンプレートに沿って要約し、
  回答ルールは「守るべきルール」として要約の中に記録していた。
- 1M 付近の長文では、記憶の劣化より先に **安全分類器の誤検知で応答が止まる** ケースがあった（1 件）。

## 1. 目的と方法

コンテキストが長くなるにつれて性能が劣化する現象（context rot）を、API を使わずサブスクリプションの範囲で検証した。

### 実行方法

すべての試行は Claude Code CLI を `claude -p` でスクリプトから呼び出して行った。

| 実験 | 呼び出し方 | 何を測るか |
|---|---|---|
| E5（会話） | Claude Code 標準のシステムプロンプト。`--session-id` / `--resume` で 1 セッションを毎ターン伸ばす。compaction の閾値は環境変数 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` | 序盤に伝えた情報を、長い会話と compaction の後も覚えているか |
| E6（単発） | 短い固定システムプロンプト・ツールなし。長文と質問を 1 回で渡す | 1 回の入力の長さ（100K〜900K）で精度が落ちるか |

共通の設定: `--safe-mode` と `--setting-sources local`（CLAUDE.md・メモリ・ユーザー設定を除外）、
リポジトリと無関係な名前のフォルダで実行、200K を超える入力には `[1m]` 付きのモデル名、effort は medium。

長文の素材はパブリックドメインの文章（日本語: 夏目漱石 6 作 約 124 万字、英語: *War and Peace*・*Moby-Dick* 約 443 万字）。
仕込む値はすべて試行ごとにランダム生成し、採点は機械的に行った（値のパターンを抜き出して照合）。

## 2. E5: 長い会話での記憶と compaction

### 設定

- 序盤 3 ターンに、承認コード 10 個・ポート番号 5 個（全体の 4 割の地点で値を変更）・回答ルール 3 つ
  （「【要約】で始める」「（以上）で終える」「3 行以内」）を分けて伝える
- 毎ターン約 15K トークンの文章を渡して要約させ、17 ターン（論理長 約 300K）まで伸ばす
- 100K / 200K / 最終の時点で、分岐セッション（`--fork-session`）から全項目を質問する。
  確認はツールなし・compaction なしで行い、本流の会話には影響させない
- compaction の要約をセッションログから取り出し、仕込んだ値がいくつ残ったかを数える

### 結果（最終時点）

| モデル | 言語 | 閾値 | compaction | 承認コード | 更新後のポート | compaction 後のルール遵守 | 要約に残った承認コード |
|---|---|---|---|---|---|---|---|
| Haiku 5.5 | 日本語 | なし（1M） | 0 回 | 10/10 | 5/5 | （全ターンほぼ 100%） | — |
| Haiku 5.5 | 英語 | なし（1M） | 0 回 | 10/10 | 5/5 | （全ターン 100%） | — |
| Haiku 5.5 | 日本語 | 150K | 3 回 | 10/10 | 5/5 | 100% | 10/10（3 回とも） |
| Haiku 5.5 | 英語 | 150K | 4 回 | **0/10** | **0/5** | **ほぼ 0%** | **0/10（4 回とも）** |
| Opus 5.5 | 英語 | 150K | 3 回 | 10/10 | 5/5 | 100% | 10/10（3 回とも） |
| Opus 5.5 | 日本語 | 150K | 3 回 | 10/10 | 5/5 | 100% | 10/10（3 回とも） |

### わかったこと

1. **compaction がなければ、Haiku 5.5 でも 300K までは劣化しなかった。**
2. **Haiku 5.5（英語）は、compaction の要約を回答ルールの形式で書いてしまった。** 要約は
   「[Summary] …（資料のあらすじ 2 段落）… (end)」だけで、承認コードもルールも入っていなかった。
   以降の確認では全項目「unknown」、ルール遵守はほぼ 0% になった。日本語の要約も同じ形式だったが、
   冒頭に「記憶すべき情報」としてコードとルールを残していた。
3. **Opus 5.5 は compaction 用の構造化テンプレート（「1. Primary Request and Intent」…）に沿って要約し、**
   回答ルールを要約自体には適用せず、「この会話で守るべきルール」として記録した。
4. 会話中の形式に関する指示（CLAUDE.md の文体ルールのようなもの）が compaction の要約を偏らせ、記憶を失わせる経路がある。
   この条件では、長さそのものより要約の質の方が記憶を大きく左右した。

## 3. E6: 単発の長文入力

### 易しい版（Opus 5.5）

1 本の長文に、点検番号 20 個（深さ 2.5〜97.5% に均等配置）、前半で示し後半で訂正する在庫数 5 個、
7〜15 回現れる一文（紫色の風船）を仕込み、まとめて質問した。

| 長さ（実測） | 日本語 | 英語 |
|---|---|---|
| 約 100K | 満点（10 秒） | 満点（10 秒） |
| 約 300K | 満点（17 秒） | 満点（9 秒） |
| 約 590K | 満点（16 秒） | 満点（13 秒、seed=1 でやり直し） |
| 約 890K | 満点（14 秒） | 満点（13 秒） |

訂正前の古い値を答えたケースもゼロ。英語 600K の 1 回目は、応答の途中で安全分類器に止められ、
Claude Code の自動再送でもモデルが回答を拒否したため除外し、文章の切り出し位置を変えてやり直した。

### 難しい版（Opus 5.5・日本語）

| 種類 | 内容 | 887K | 97K（対照） |
|---|---|---|---|
| 言い換え | 記録と質問で語彙をずらす（「測候所の男が毎朝のぼる石段」→「気象観測施設の職員が通勤で登った段数」） | 8/8 | 8/8 |
| ディストラクタ | 似た名前・別の建物・改番前の旧番号を混ぜる | 5/5 | 5/5 |
| multi-hop | 「〇〇さんは青組」（前半）＋「青組の集合場所は△△」（後半） | **4/5** | 5/5 |
| 複数回更新 | 4 回更新される値の最新値・最初の値 | 6/6 | 6/6 |
| 条件つき数え上げ | 紫色の風船 7 回（赤い風船 8 回・紫色の凧 12 回が紛れる） | **誤り（8 回）** | 正解 |
| 応答時間 | | 147 秒 | 18 秒 |

同じ 887K の文章に質問を分けて聞くと（5 人の所属組、5 組の集合場所、紫色の風船の記録の列挙）、**全問正解**した。

### わかったこと

- 個々の記録は 887K でもすべて見つけられる。失敗したのは、**離れた 2 か所を 1 回の回答の中で結びつける**ことと、
  **紛らわしい記録の中から条件に合うものだけを数える**こと。
- 同じ課題が 97K なら満点なので、難しさだけでなく長さが効いている。1M 付近の劣化は単純な検索ではなく
  「統合・集計」が要る課題に出る。これは先行研究とも整合する。
- 「列挙してから数える」ように質問を分解すれば、887K でも正しく数えられた。

## 4. 方法論上の知見（サブスクリプションで検証するときの落とし穴）

| 問題 | 症状 | 対策 |
|---|---|---|
| Windows の `claude.CMD` | プロンプト引数に改行があるとコマンドラインが切れ、後続のフラグ（`--safe-mode` など）が黙って落ちる | 本文はすべて stdin で渡す |
| 作業フォルダの名前 | パスやリポジトリの情報から検証中だと推測され、作業を断られた | 無関係な名前のフォルダで実行する |
| `--autocompact` フラグ | `-p` + `--resume` では効かない | 環境変数 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` を使う（発火点は指定値の約 33K 手前） |
| モデル名 | `claude-haiku-5-5` は 200K を超えると「Prompt is too long」 | `[1m]` 付きの名前を使う |
| ユーザー設定 | `--safe-mode` でも `"language": "japanese"` が残り、英語条件を汚す | `--setting-sources local` |
| 確認の質問でのツール | compaction 後、モデルが元の会話ログを探しに行き、見つからないと全項目「不明」と答える | 確認はツールなし・「記憶だけで答えて」 |
| 分岐セッションでの compaction | 確認用の分岐で再度 compaction が起き、2 回目の要約で事実が消える | 確認時は窓を最大にする |
| 合成したフィラー文 | 英語の合成文が安全分類器に `[bio]` として誤検知された | 本物の文章を使う |
| needle の言葉 | 「暗証番号」がプロンプトインジェクション扱いで拒否された | 中立的な事実にする |
| JSON 形式の確認 | `code:Basalt` のような機械的なキーは対応づけられず全項目 null | 自然な日本語・英語のキーにする |

## 5. 利用量（Max 5x）

| 実行 | 処理トークン（概算） | 5 時間枠 | 週 |
|---|---|---|---|
| Phase 0（Haiku） | 約 250 万 | +2% | ±0 |
| E5 Haiku 4 セッション（300K） | 約 1,000 万（大半がキャッシュ読み込み） | +1% | ±0 |
| E5 Opus 1 セッション（300K） | 約 175 万（大半がキャッシュ読み込み） | +2% | ±0 |
| E6 Opus 9 回（100K〜900K、新規入力） | 約 560 万（すべてキャッシュ書き込み） | +19% | +3% |
| E6-hard 887K＋追加質問＋97K | 約 190 万（すべてキャッシュ書き込み） | 約 +6% | — |

- 会話形式は前ターンまでがキャッシュ読み込みになるため安い（Opus で 100 万トークンあたり 5 時間枠の約 1%）。
- 毎回新しい長文を送る単発試行は割高（Opus で 100 万トークンあたり約 3〜4%）。
- 文章と質問を 1 メッセージで送る形では、同じ文章への追加質問でもキャッシュが効かなかった。
- 安全分類器の拒否が起きると、自動再送で入力が 2 回分計上される。

## 6. 限界

- ほとんどの条件が 1 回のみ（seed 1 つ）。日英差や E6-hard の誤りの再現性は未確認。
- E5 は最終長 300K まで。会話形式で 1M 付近まで伸ばす実験は利用量の都合で行っていない。
- 仕込んだ情報は括弧書きの記録で、実際の作業（コード、ツール結果）とは性質が違う。
- 本文の内容そのものの理解（長い文章を読んで答える問題）は扱っていない。

## 7. 次の課題

- E6-hard の誤りの再現性（seed を変えて 887K を数回）
- 会話形式での 1M 付近（1 ターンを大きくしてターン数を抑える）
- 回答ルールの有無で Haiku の compaction 失敗が再現するかの切り分け
- 文章だけのターンを先に送り、質問を別ターンにしてキャッシュを再利用する実装
